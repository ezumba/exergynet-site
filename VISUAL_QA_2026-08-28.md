# Visual QA — 2026-08-28

**Directive:** VP Sales Directive 008 §9
**Status: NOT complete.** Per the directive's own instruction — "if environment still prevents this, document the blocker and do not claim visual QA complete" — this report documents what was and was not possible this session, and does not claim the full visual QA checklist was satisfied.

---

## Environment constraint

The Browser pane used for this session's automation is not displayed on the user's side. Two consequences, discovered and confirmed during this pass rather than assumed from an earlier session's note:

1. **Screenshots fail outright.** `computer{action:"screenshot"}` returns: *"Screenshot timed out after 5s: the Browser pane is not displayed, so the page is not compositing frames."* This blocks every item on the directive's checklist that requires actually looking at the page — fold, typography, CTA visual hierarchy, clipping, card layout, figure/screenshot rendering.
2. **Geometry-based JavaScript checks are unreliable as a substitute.** An attempt to detect horizontal overflow via `window.innerWidth` / `document.documentElement.scrollWidth` produced two clear measurement artifacts: a `window.innerWidth` reading of `0` immediately after a plain page load (before any explicit viewport size was set), and an unexplained mobile-width reading of `555` instead of the requested `375` on one page. Both are attributable to the lack of real compositing, not real page geometry. Confidence in any overflow finding from this method is accordingly downgraded to "possible, needs real visual confirmation" rather than "confirmed."

**What remained reliable and was used instead:** HTTP status of every linked page, presence of broken images (`naturalWidth === 0` after load — a DOM-level fact, not a rendering one), full link-target harvesting and resolution, DOM-level element inspection (real tag/attribute checks rather than accessibility-tree summaries, which also showed gaps — see below), and functional click-through (the mobile hamburger menu was actually clicked and its result inspected, not just assumed present).

## Pages checked

Homepage (`index.html`), `benchmarks.html`, `enterprise.html`, `design-partner.html`, `security.html`, `docs.html`, `machines.html`, `connect.html`, `faq.html`, `mcp.html` — all ten pages named in the directive.

## What was confirmed, reliably, for every page checked

- **All 32 distinct internal page links resolve HTTP 200.** No dead internal navigation anywhere in the set checked.
- **Zero broken images** (`naturalWidth === 0`) on any page checked.
- **External/well-known link targets from the homepage all resolve**: `.well-known/exergynet.json`, `llms.txt`, `.well-known/ai-plugin.json`, `portal.exergynet.org`, `storage.exergynet.org`, `github.com/ezumba/vanguard-memory-node` — all HTTP 200.
- **Mobile nav is functional, not just present.** At 375px width, the header collapses to a hamburger button (`aria-label="Menu"`); clicking it (an actual click event, not an assumption) reveals all 9 primary nav links with correct `href` targets. No horizontal overflow was measurable at the `<body>` level on mobile for any page (though see the geometry-reliability caveat above).
- **A tooling false alarm, corrected before reporting:** the accessibility-tree-based `read_page`/`find` tools initially appeared to show the homepage's primary CTAs ("See the Measured Results," etc.) as non-interactive — direct DOM inspection confirmed they are real, correctly-formed `<a href="...">` elements. This was a limitation of the summarization tool, not a site defect, and is noted here so it isn't mistaken for a real finding.

## Real findings — verified, not assumed

1. **`docs.html` links to a dead endpoint.** `https://explorer-api.exergynet.org/command.html` returns 404; the bare domain root also 404s. Unclear whether this is a wrong path (the API is real but this isn't a valid page on it) or the service itself is down — needs the operator to confirm the intended target.
2. **Site-wide Discord link inconsistency.** The nav/footer "Discord" link on nearly every page (homepage, docs, machines, connect, faq, mcp, and by extension the shared header/footer template) points to `discord.com/channels/1500548202384986203/1500548202959732970` — a channel-permalink format that requires the visitor to already be a server member. `connect.html` alone uses the correct public-invite format, `discord.gg/EXERGYNET` (confirmed to redirect properly to `discord.com/invite/EXERGYNET`). A new visitor clicking "Discord" from almost anywhere on the site does not get a working join flow.
3. **First-party `mcp.html` documents a non-functional, undisclosed pseudo-API.** The page describes an HTTP+Ed25519-signed "MCP Gateway" (`https://exergynet.org/mcp`) with an `exergynet_open_job` method whose example code instructs signing the request with a real Solana private key to "lock" 0.002 SOL, with a documented success response ("Your agent is now cleared to broadcast the... lock transaction"). A safe probe — a bare `POST` with no real signature, and a `GET` — confirms this endpoint is **not implemented**: `POST` returns a generic static-server `405`, and `GET` just serves the same static HTML documentation page verbatim (`Content-Type: text/html`, same page title). The page's existing "STATUS NOTICE" box says on-chain proof verification is "in development" but does not disclose that this specific signing flow has no backend at all. This is a content-accuracy and safety-messaging issue, not a live exploitable path (nothing real is signed or broadcast because the endpoint doesn't process requests) — but it describes exactly the autonomous-private-key-signing pattern this whole incident chain has been correcting elsewhere in the codebase, and reads as a working capability to anyone who doesn't test it. **Not corrected this pass** — this is a product/content decision (label as unimplemented, or remove the section) rather than a copy-edit, and is flagged for the operator rather than acted on unilaterally.
4. **Possible (unconfirmed) desktop overflow on `security.html`.** A `scrollWidth` check flagged 174px of overflow at 1440px width, traced to a single `.glow-accent` decorative `<div>` (560px wide, absolutely positioned, intentionally bleeding off the right edge — `right: -180px` — for a glow visual effect). `<body>` already has `overflow-x: hidden` set, which is the standard mitigation for exactly this pattern and, in a normally-composited browser, should prevent any visible scrollbar or clipping. Given this session's already-demonstrated unreliable geometry measurements in the non-composited pane state, **this is reported as unconfirmed, not as a defect** — it should be spot-checked visually once the pane can be displayed, but there is a plausible, standard explanation for why it may not be a real user-facing problem at all.

## What still needs a real visual pass

Fold position, typography rendering, exact CTA visual hierarchy/prominence, card layout at intermediate breakpoints, footer layout, and actual screenshot evidence for any of the above — none of this was possible without compositing. The `security.html` overflow question above specifically needs eyes-on confirmation. Recommend re-running this checklist with the Browser pane displayed, at which point full screenshot-based QA (desktop + mobile, per page) becomes possible and should be done before any press/analyst traffic is directed at the site, per Directive 008 §9's own instruction.
