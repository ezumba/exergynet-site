# LNES-59 Execution Chronology Erratum

**Status: APPEND-ONLY. Does not modify, does not supersede, and is not a
correction to the scoring in any sealed artifact.** No sealed source file
(`LNES59_HOLDOUT_MANIFEST.json`, `LNES59_EXPERIMENT_MANIFEST.json`,
`LNES59_FINAL_RESULTS_MANIFEST.json`, `LNES59_FINAL_VALIDATION_REPORT.md`,
`evaluator_aggregate_output.json`, `LNES59_EXECUTION_LEDGER.json`,
`raw_results/`) was altered to produce this note.

## The discrepancy

Two different-sounding figures appear in the historical record of this
execution:

1. **"312/400 subagent-generated, 88/400 direct-generated"** — appears in
   `LNES59_FINAL_RESULTS_MANIFEST.json`'s `execution_summary.generation_mechanism`
   field.
2. **"320/400 complete before direct execution, 80/400 remaining"** — appears
   in the conversational narrative at the point where the Agent-tool
   subagent-dispatch mechanism hit its 200-agent per-session spawn limit.

These are not actually in conflict; they measure two different things.

## Reconstruction

`LNES59_EXECUTION_LEDGER.json` records 400 entries, one per case-arm pair,
each with a `status` and `completion_timestamp`, but does not record which
mechanism (subagent dispatch vs. direct execution) produced each entry.
Mechanism provenance is therefore reconstructed from the case-number
boundary, which is unambiguous and independently checkable:

- Every case-arm pair for **H01 through H39** (39 cases × 8 arms = **312
  pairs**) was generated by dispatching an Agent-tool subagent
  (`subagent_type="claude"`, `run_in_background=true`) that read its
  `prompts_txt/{case_id}__{arm}.txt` file and wrote its JSON answer to
  `generation_responses/`.
- All 8 arms for **H40** failed to dispatch — every H40 Agent-tool call in
  that batch returned `"Subagent spawn limit reached (200 of 200 agents
  spawned)"` — and were instead generated by directly reading the prompt
  file and writing the JSON response in the same turn, without a subagent.
  The same direct-execution mechanism was used for all remaining cases,
  **H40 through H50** (11 cases × 8 arms = **88 pairs**).
- 312 + 88 = 400, matching `LNES59_EXECUTION_LEDGER.json`'s total entry
  count and `evaluator_aggregate_output.json`'s `n_total_records: 400`
  exactly. This confirms figure 1 ("312/400 subagent-generated, 88/400
  direct-generated") is the correct **final generation-mechanism split**.

Figure 2 ("320/400 complete... 80/400 remaining") was a different
measurement: a `collect_and_persist.py` output printed at one specific
checkpoint during execution, reporting how many case-arm pairs had been
*persisted to `raw_results/`* at that moment — a point-in-time snapshot of
collection progress, not a claim about the generation-mechanism boundary.
Collection ran in batches slightly offset from generation (a batch of
already-generated `generation_responses/*.json` files would sometimes sit
uncollected for one or more turns before the next `collect_and_persist.py`
run), so a persistence-count snapshot taken mid-run does not line up
cleanly with the H39/H40 case boundary — it was never intended to. The
"320" and "80" figures are correct as a description of that one moment's
collection state; they are not a competing claim about which pairs were
subagent- vs. direct-generated.

## Which historical files/turns contain the inconsistent wording

- The conversational turn immediately after the spawn-limit error stated
  "320/400" as a `collect_and_persist.py` completion count, in a context
  discussing the transition to direct execution — this juxtaposition is
  what makes it read, out of context, as if "320" were the subagent/direct
  boundary. It was not; see reconstruction above.
- `LNES59_FINAL_RESULTS_MANIFEST.json`'s `execution_summary` field states
  the correct 312/88 mechanism split and required no correction.

## Scores are unaffected

Both mechanisms used the identical frozen prompts (`prompts_txt/*.txt`,
generated once by `explode_prompts.py` from `precomputed_prompts/*.json`,
before either generation mechanism ran), the identical
`CANDIDATE_CLAIM_SCHEMA_INSTRUCTIONS`, and were scored by the identical
unmodified `comparator_metrics.py`. Direct execution for H40-H50 was
disclosed in `LNES59_FINAL_VALIDATION_REPORT.md` §21/§23 at the time the
report was written — this erratum resolves a wording ambiguity about the
*count*, not a previously-undisclosed fact about the mechanism itself.
**No metric, hash, or headline result in any sealed artifact changes as a
result of this erratum.**
