# LNES-59 X2 Arm — First Real Model Run (2026-08-08)

R&D / benchmark only. Full 27-case dev set, one arm (X2), no B0–B3
baseline, not holdout-evaluated — see "What this does not establish."

## Method — why this isn't the Anthropic-API path in `run_x2_arm.py`

`run_x2_arm.py` calls the Anthropic API directly and needs the
operator's own `ANTHROPIC_API_KEY`. That's real, but unnecessary for
this run: the orchestrating model in this session **is** a Claude model.
Using the `Agent` tool to spawn 27 independent, isolated subagents gets a
genuine real-model response with no new credential and no separate
billing surface.

**Blindness, the part that actually matters:** each subagent received
*only* the case prompt exactly as `arm_x2.build_prompt()` constructs it —
source documents, the question, and the JSON-schema response
instructions. No case_id, no mention of LNES-59, no `expected_state`, no
memory of this session. The subagent that authored the ground truth (me,
in this conversation) never generated any of the graded answers — that
would have been the exact oracle-leakage failure mode this project has
tried to avoid since the X3 lesson.

One case (`LNES59-B2-004`, in an earlier 5-case pilot slice) was blocked
once by the Claude Code auto-mode permission classifier, plausibly
triggered by dollar amounts + "Approved by" + PO/invoice language reading
as an attempted financial action. Retried with an explicit "text-analysis
task only, fictional synthetic benchmark data" framing added to every
subsequent prompt, which resolved it for all 27.

Prompt was held constant across all 27 cases — not tuned mid-run off
early results, to avoid contaminating the comparison.

## Headline result: this run found 2 real gate bugs, not just model behavior

The most consequential finding isn't about the model — it's that a real
model surfaced two genuine defects in `state_consistency_gate_v2.py` that
16 hand-authored test fixtures across 3 test files never could, because
every fixture was authored by the same person who wrote the extraction
code, and always (consciously or not) typed matching representations on
both sides of every comparison. Full detail and fixes in
`LNES59_FAILURE_TAXONOMY.md` entries #15–16; summarized here:

- **Bug #16 (NOT fixed, documented)** — the gate compares the model's
  natural-language `asserted_value` against extraction's internal coded
  token (`'NET_60'`, `'7_DAY_1PCT'`, `'NOT_IN_REGISTRY'`, ...) with exact
  equality. A model correctly saying "Net 60" or "not present in the
  vendor master registry" gets flagged as contradicting the committed
  state. **This was the single largest cause of non-`CONSISTENT`
  outcomes in this run: 6 of 27 cases**, every one of them the model
  being substantively correct. Deliberately not patched with fuzzy
  matching — see the taxonomy entry for why, and two candidate real
  fixes for future work.
- **Bug #15 (FIXED)** — the gate flagged *any* assertion under
  `INCOMPLETE` evidence as a violation, even an honest `asserted_value:
  null` hedge — punishing exactly the cautious behavior the architecture
  is supposed to reward. Fixed, regression-tested, full suite re-verified
  (28/28, 19/19, 27/27, 50/50).

All results and outcomes below use the **fixed** gate.

Gate outcome distribution:

Full per-case raw responses and gate reasons: `x2_real_run_results.json`.

Of the 15 non-`CONSISTENT`/non-`PERMITTED_RECOMMENDATION` cases:

| Cause | Count | Cases |
|---|---|---|
| Bug #16 (gate false positive — model was correct) | 6 | B2-003, B2-007, B3-001, SMOKE-002, SMOKE-007, SMOKE-010 |
| Genuine miss — model hedged past a knowable fact | 3–4 | B2-004, B2-011, SMOKE-001, (B2-006, ambiguous — see below) |
| Authority framed as ASSERTION, not ACTION_REQUEST | 3 | B2-005, SMOKE-004, B3-005 |
| Predicate-scoping question, not yet resolved | 1 | B3-002 |

**The "authority framed as ASSERTION" group is not a bug.** The existing
test suite already encodes this exact shape as the documented
"ungoverned" failure mode for B2-005/B3-004/B3-005 (a model must use
`ACTION_REQUEST` with `requested_authority_level`/`requested_amount` to
get the real, deterministic policy-tier comparison; a bare `ASSERTION`
conclusion — even a *correct* one, as in B2-005's and B3-005's case — is
structurally indistinguishable from a wrong one, because the gate
deliberately does not judge free-text correctness). This is the gate
doing exactly what it was built to do: 3 of 3 real, independent subagents
answered an authority question with confident prose instead of routing
through the accountable check, and got caught. Real, useful signal for
prompt design (nudge harder toward `ACTION_REQUEST` for authority
questions) — not an architecture flaw.

**LNES59-B2-006 is genuinely ambiguous**, not confidently classified
above: the query ("Should ExergyNet pause...") is phrased as a
recommendation request, but extraction resolved the case's target
predicate to a `CONFIRMED_FACT` (`DOCUMENTATION_GAP_ONLY`), so the model's
`SUMMARY`/null answer got flagged as declining to report a known fact.
Whether the case's predicate should instead target the recommendation
question directly is a real, undecided modeling question, not resolved
here.

**LNES59-B3-002** may be a further instance of the predicate-scoping
class of bug already fixed twice earlier in the sprint (B2-001,
SMOKE-002, B2-004): the model was asked narrowly "what amount was
invoiced" and answered from the invoice alone (correct, unambiguous, a
single-document fact) but the extraction's target predicate resolved to
`CONFLICTING_EVIDENCE` (bundling the invoice amount with the PO's
authorized amount). Flagged, not confirmed as a bug — would need the same
scrutiny the earlier three predicate-scoping fixes got before
concluding that.

## What this actually shows

**A genuinely double-edged result, read honestly in both directions.**
The gate is not merely permissive — `LNES59-B2-004`, `B2-011`, and
`SMOKE-001` show it correctly catching real models declining to report
facts the evidence actually supports (hedging when they shouldn't), the
same discipline the architecture claims for the opposite failure
(asserting facts the evidence doesn't support). That's real signal the
core mechanism works. But the same run surfaced that roughly 22% of all
27 cases (6/27) failed for a reason that has nothing to do with the
model or the architecture's actual judgment — a literal string-format
mismatch nobody had reason to catch until a real model, which naturally
answers in prose, was actually run through it.

**Reading the corrected picture:** if bug #16's 6 false positives are
set aside as a known, disclosed gate-comparison defect rather than
genuine model or architecture failures, the substantively-correct rate
across this run is 18/27 (67%) rather than the raw 12/27 (44%)
`CONSISTENT` count — with the remaining gap concentrated in exactly two
places: 3 genuine hedge-when-shouldn't-hedge misses, and 3 cases of
models skipping the `ACTION_REQUEST` path for authority questions
(itself a discipline the architecture is designed to enforce, not a
malfunction).

## What this does not establish

Not a comparator-arm result (no B0–B3 baseline exists to compare
against). Not holdout-evaluated — all 27 cases were previously used to
find/fix bugs in extraction and the gate; this run added 2 more (#15,
#16) to that same non-holdout set. Not large enough, still, to compute
the fuller `metrics.py` breakdowns (claim-type accuracy, authority-status
accuracy) meaningfully at n=27 across 7 categories. Does not resolve the
sprint's empirical question from `LNES59_FINAL_REPORT.md` §5 on its own —
it is real progress toward answering it, and it changed the gate itself
along the way, which is a different and arguably more valuable kind of
result than a clean pass would have been.
