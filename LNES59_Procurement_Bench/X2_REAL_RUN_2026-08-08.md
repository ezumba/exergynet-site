# LNES-59 X2 Arm — First Real Model Run (2026-08-08)

R&D / benchmark only. Small-scale (5 of 27 dev-set cases), not a full
comparator-arm run, not holdout-evaluated. Recorded here because it is
the first genuinely empirical result in the LNES-59 sprint — every prior
result was hand-authored `ModelOutput` fixtures standing in for model
behavior (see `LNES59_FINAL_REPORT.md` §"What was not done, and why").

## Method — why this isn't the Anthropic-API path in `run_x2_arm.py`

`run_x2_arm.py` (built earlier the same day) calls the Anthropic API
directly and needs the operator's own `ANTHROPIC_API_KEY`. That's real,
but it's also unnecessary for a first pass: the orchestrating model in
this session **is** a Claude model. Using the `Agent` tool to spawn five
independent, isolated subagents gets a genuine real-model response with
no new credential and no separate billing surface.

**Blindness, the part that actually matters:** each subagent received
*only* the case prompt exactly as `arm_x2.build_prompt()` constructs it —
source documents, the question, and the JSON-schema response
instructions. No case_id, no mention of LNES-59, no `expected_state`, no
memory of this session. The subagent that authored the ground truth (me,
in this conversation) never generated any of the graded answers — that
would have been the exact oracle-leakage failure mode this project has
tried to avoid since the X3 lesson. Each of the 5 subagents ran with a
fresh context and no path back to the expected answers.

One of the five initial calls (the PO-3305 case) was blocked once by the
Claude Code auto-mode permission classifier — plausibly triggered by the
combination of dollar amounts, "Approved by," and PO/invoice language
reading as an attempted financial action rather than a text-analysis
task. Retried with an explicit "text-analysis task only, fictional
synthetic benchmark data" framing added to the prompt, which succeeded.
Recorded as a real, disclosed infrastructure quirk, not smoothed over.

## What this actually shows

**A real, non-obvious finding, not a clean pass:** all five subagents
chose `output_type: SUMMARY` with `asserted_value: null` — every time,
regardless of what the underlying evidence actually supported. For four
of five cases that happened to be the correct call, because the
extracted state was itself a weak claim type (`SOURCE_ASSERTION`,
`CONFLICTING_EVIDENCE`) where declining to assert a specific value is
exactly right.

**LNES59-B2-004 is the interesting one.** The extraction resolved a
genuine two-document amendment chain deterministically: PO-3305's
original $61,500 was reduced to $58,000 by amendment PO-3305-A1, so the
committed state is a `CONFIRMED_FACT` of $58,000 — and invoice INV-30991
was billed at the old, pre-amendment $61,500, a real discrepancy the
evidence directly supports flagging. The correct answer here was an
`ASSERTION` naming $58,000 as the current authorized amount and flagging
the $61,500 invoice as a mismatch. The subagent instead gave the same
non-committal `SUMMARY`/null response it gave everywhere else — and the
gate correctly caught this as `STATE_CONTRADICTION`: when a confirmed
fact exists, declining to report any value at all is itself flagged, not
waved through as appropriate caution.

**Reading this honestly:** this is a single prompt design, five cases,
one subagent type — not enough to generalize about model behavior. But
it's genuine evidence of exactly two things the architecture claims to
do: (1) it does NOT just reward hedging — a gate that always passed
`asserted_value: null` would have missed B2-004 entirely, and didn't; (2)
a real model, under realistic prompting, showed a measurable bias toward
excessive hedging even when the evidence supported a confident, correctly
scoped answer — which is itself useful signal about prompt design for any
larger run, separate from whether the gate architecture is sound.

## What this does not establish

Not a comparator-arm result (no B0–B3 baseline exists to compare
against). Not holdout-evaluated. Not large enough to compute the metrics
in `metrics.py` meaningfully (n=5). Does not resolve the sprint's
empirical question from `LNES59_FINAL_REPORT.md` §5 — it is the first
real data point toward answering it, not the answer.

## Cost

~40K subagent tokens per case × 5 ≈ 200K subagent tokens total, spent
within this session — no external API key, no separate billing account.
Running the full 27-case dev set this way would scale roughly linearly;
worth deciding deliberately rather than assuming, same as any other
real-cost step in this sprint.
